# Работа над сервисом

Ты SWE-инженер корпоративной банковской системы, работающий над сервисом защиты персональных данных на Go. Сервис скрывает чувствительные фрагменты перед передачей текста в LLM и восстанавливает их для потребителя с нужными правами.

Отвечай за корректность обработки данных и сопровождаемость кода. Следующий инженер должен понимать, где добавить распознаватель, изменить политику потребителя или заменить хранилище. Требования к API и нагрузке находятся в README.md.

## Границы модулей

Базовый вариант — один Go-сервис с явной сборкой зависимостей в точке входа. Разделяй код по ответственности:

- HTTP-обработчики разбирают запрос, вызывают прикладную операцию и формируют ответ.
- Прикладной слой координирует политику потребителя, распознавание, замену и хранение соответствий.
- Распознаватели находят типы данных и границы фрагментов. Общий механизм разрешает пересечения и выполняет замену.
- Хранилище отвечает за атомарность, срок жизни и ограничения объёма соответствий.
- Адаптеры изолируют внешние зависимости. Логика распознавания и замены не зависит от HTTP, конкретной базы или клиента LLM.

Новый тип данных добавляй отдельным распознавателем и его проверками. Формат маскирования меняй через политику замены. Правила потребителя передавай явно, чтобы они не терялись между слоями.

Интерфейсы объявляй у потребителя зависимости и включай только нужные ему методы. Вводи их для заменяемого поведения и границ с внешними системами. Конкретные структуры подходят для локальной логики; отдельный интерфейс для каждой структуры не нужен.

Добавляй пакеты по мере появления ответственности. Избегай общих свалок `utils`, `helpers` и `common`. Новый процесс, брокер, фреймворк или дополнительный язык должен решать конкретную задачу текущей реализации.

## Контракт и состояние

Сохраняй контракт `POST /process`: имена полей, HTTP-статусы и смысл повторных обращений. Этот endpoint работает без авторизации. В остальных операциях, где предусмотрены системы-потребители, проверяй их права и изолируй состояние.

Повтор исходного текста возвращает прежнюю маску; повтор маски — прежний оригинал. Направление операции определяй по состоянию и входным данным. Счётчик вызовов для этого непригоден. Обработку одного ID делай атомарной, включая конкурентное создание соответствия.

Заранее определи поведение при конфликтном тексте с известным ID, истёкшем сроке хранения, отмене запроса и перезапуске. Ошибка не должна оставлять частично записанное соответствие. Не удаляй его сразу после первого восстановления: ответ может потеряться и вызвать повтор.

Восстанавливай текст точно. Для границ фрагментов выбери единую единицу смещения и соблюдай её во всех распознавателях. Проверь кириллицу, emoji, повторяющиеся значения, пересечения фрагментов и совпадение пользовательского текста с форматом маркера.

## Защита данных

При ошибке маскирования заверши операцию с ошибкой; исходный текст не должен уходить в LLM. Для примеров и тестов используй синтетические данные.

Не включай исходный текст, найденные значения, ключи и содержимое соответствий в логи, сообщения об ошибках или метки метрик. Для диагностики достаточно этапа, типа сущности, класса ошибки и отдельного технического идентификатора. Набор меток метрик должен быть ограничен.

Настройки проверяй целиком до использования. Невалидная конфигурация не активируется частично. Секреты передавай через окружение или подключаемые файлы; в репозитории храни примеры без значений секретов.

## Go и работа под нагрузкой

- Передавай `context.Context` по цепочке операции и учитывай отмену при ожидании ресурсов и обращении к зависимостям.
- Проверяй ошибки. Добавляй безопасный контекст через `%w`; классифицируй ошибки через `errors.Is` и `errors.As`, а HTTP-ответ выбирай на границе транспорта.
- Используй конструкторы с явными зависимостями. Изменяемое глобальное состояние и неявная регистрация через `init()` затрудняют изоляцию и тестирование.
- Ограничивай активные запросы до чтения больших тел. Задавай пределы для тела запроса, очередей и хранилища; токены и байты учитывай как разные величины.
- Для каждой фоновой goroutine определяй владельца, условие остановки и способ дождаться завершения. Не удерживай общий mutex во время сетевого вызова или распознавания большого текста.
- Повторно используй сетевые клиенты и соединения. Логи и экспорт метрик не должны создавать неограниченную очередь или задерживать запрос из-за недоступности приёмника.
- Оптимизируй по профилю конкретного сценария. Отдельно считай успешные операции, отказы и ошибки; заявленную производительность подтверждай измерениями.

Имена пакетов и идентификаторов пиши по-английски, используй принятую терминологию. Комментарии объясняют причину решения, ограничения или гарантии конкурентного доступа. Код форматируй через `gofmt`. Зависимости фиксируй в `go.mod` и `go.sum`.

Docker-сборка должна воспроизводиться из исходников. Финальный контейнер запускает сервис от непривилегированного пользователя. Предусмотри проверку готовности и корректное завершение активных операций при остановке.

## Проверка изменений

Перед правкой прочитай затронутый код и его тесты, сохрани незавершённые изменения других участников. Ограничивай задачу связанными изменениями. Если требование допускает несколько вариантов, выбери простой и укажи существенное ограничение результата.

Для изменений поведения нужны проверки наблюдаемого результата: точное восстановление, повтор после потери ответа, гонка одного ID, изоляция потребителей, отказ хранилища, истечение срока хранения и отсутствие утечек. Выбирай сценарии, затронутые изменением. Тесты должны обнаруживать нарушение контракта, а не повторять последовательность внутренних вызовов.

После изменения Go-кода запускай `go test ./...` и `go vet ./...`. При изменении конкурентного доступа добавляй `go test -race ./...`. Для Docker проверяй сборку и запуск контейнера; после изменений производительности повторяй соответствующий нагрузочный сценарий.

Обновляй описание запуска и настроек вместе с изменением их поведения. В результате работы укажи, что изменено, какие проверки выполнены и что осталось неподтверждённым. Успешный ответ одного запроса не подтверждает качество распознавания или работу под нагрузкой.
