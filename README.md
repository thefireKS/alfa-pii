# Сервис защиты персональных данных

Go-сервис маскирует персональные данные в тексте и восстанавливает их по идентификатору запроса. Реализовано распознавание семнадцати категорий данных и полный цикл маскирование → восстановление.

## Запуск

```sh
go run ./cmd/pii-service
```

Сервис слушает `:8080` по умолчанию. Настройки задаются переменными окружения, см. `config/config.example.env`. Невалидная конфигурация отклоняется целиком до запуска.

### Краткая инструкция настройки

1. Скопируйте `config/consumers.example.json` в свой файл и укажите в нём системы, их типы, права и формат маски. 2. Задайте секреты через переменные окружения, имена которых указаны в файле (`secret_env`), например `PII_CONSUMER_ALPHA_SECRET`. 3. Укажите путь к файлу в `PII_CONSUMERS_FILE`. 4. Запустите сервис; невалидная конфигурация остановит старт. 5. Обращайтесь к `/v1/mask` и `/v1/restore` с заголовком `Authorization: Bearer <секрет>`.

## Docker

Многоэтапная сборка воспроизводима из исходников. Версия Go берётся из `go.mod` (`1.27.1`), образы и зависимости фиксируются явно (по digest). Финальный образ — `gcr.io/distroless/static-debian12:nonroot`: содержит только исполняемый файл, запускается от непривилегированного пользователя (UID 65532), без shell и curl. Настройки и секреты подключаются при запуске и не попадают в образ.

### Сборка и запуск

```sh
# Собрать образ и запустить контейнер (порт 8080)
make build
make run

# Проверка готовности (с хоста; в образе нет curl)
make health          # GET /livez и /readyz

# Полный цикл /process: маска -> повтор -> восстановление -> конфликт 409
make process

# Демонстрация цикла маскирование -> модель -> восстановление
# против запущенного контейнера (потребитель demo)
make demo

# Логи, статус, остановка
make logs
make ps
make stop
```

Локальная конфигурация запуска — `docker-compose.yml`: явные порты (`8080:8080`), лимиты ресурсов (2 CPU, 512 MiB), read-only корневая ФС, writable `/tmp` (tmpfs 64 MiB), файл потребителей монтируется read-only. Секрет демо-потребителя задаётся в `.env` (см. `.env.example`, переменная `PII_CONSUMER_DEMO_SECRET`); `.env` исключён из сборки и не попадает в образ.

### Ограничения рестарта

Хранилище соответствий — in-memory и не является постоянным. После перезапуска контейнера все соответствия теряются:

- Ранее выданная маска обрабатывается как новый исходный текст и возвращается без изменений (формат `[PII_N]` не распознаётся как персональные данные); восстановить оригинал по маске после рестарта нельзя.
- Тот же `payload_id` с исходным текстом создаёт новое соответствие.
- Для постоянного хранения требуется замена хранилища; in-memory вариант не выдаётся за постоянное.

### Остановка и незавершённые операции

При `SIGTERM` сервис выполняет graceful shutdown: активные запросы завершаются в пределах `PII_SHUTDOWN_TIMEOUT` (по умолчанию 10 с), затем процесс выходит с кодом 0. Запрос, не успевший завершиться за этот срок, получает закрытие соединения; резервирование ключа в хранилище освобождается без частичного состояния.

## Развёртывание сервера (standalone)

Для запуска сервиса как отдельного сервера (без демонстрационных команд) используется `compose.server.yml` — конфигурация контейнера, аналогичная `docker-compose.yml`, но с отличиями:

- порт публикуется только на loopback `127.0.0.1:8000:8080` (не открывается наружу);
- секрет демо-потребителя обязателен и берётся из файла `.env.deploy` (переменная `PII_CONSUMER_DEMO_SECRET`); при отсутствии переменной `docker compose` останавливает запуск с ошибкой, а не подставляет значение по умолчанию;
- `restart: unless-stopped` — контейнер перезапускается автоматически при падении процесса;
- `stop_grace_period: 20s` — запас на graceful shutdown активных операций.

Остальные настройки совпадают с локальным запуском: read-only корневая ФС, writable `/tmp` (tmpfs 64 MiB), лимиты 2 CPU / 512 MiB, файл потребителей `config/consumers.local.json` монтируется read-only, `no-new-privileges`.

### Подготовка окружения

Секрет демо-потребителя не хранится в репозитории. Создайте файл `.env.deploy` с новым случайным секретом (файл исключён из git через `.gitignore`):

```sh
python3 init-deploy-env.py
```

Скрипт создаёт `.env.deploy` с правами `0600` и записывает в него `PII_CONSUMER_DEMO_SECRET=<случайный hex>`. Если файл уже существует, он не перезаписывается — скрипт сообщает об этом и завершается успешно. Секрет на экран не выводится. При необходимости задайте секрет вручную в `.env.deploy` (см. `.env.example`).

### Запуск и остановка

```sh
# Собрать образ и запустить контейнер (порт 8000 на loopback)
docker compose -f compose.server.yml --env-file .env.deploy up -d --build

# Проверка готовности (с хоста; в образе нет curl)
curl -fsS http://127.0.0.1:8000/readyz && echo
curl -fsS http://127.0.0.1:8000/livez && echo

# Логи, статус, остановка
docker compose -f compose.server.yml --env-file .env.deploy logs -f
docker compose -f compose.server.yml --env-file .env.deploy ps
docker compose -f compose.server.yml --env-file .env.deploy down
```

`--env-file .env.deploy` обязателен: именно из него `compose.server.yml` читает `PII_CONSUMER_DEMO_SECRET`. Без него запуск завершится ошибкой из-за обязательной переменной.

### Smoke-тест развёртывания

`smoke-deploy.py` проверяет, что развёрнутый сервис жив и соблюдает публичный контракт `POST /process` на синтетических данных (без аутентификации и без реальных персональных данных):

```sh
python3 smoke-deploy.py http://127.0.0.1:8000
```

Скрипт последовательно проверяет:

1. `/readyz` (с повторами до готовности) и `/livez` — сервис отвечает;
2. новый `payload_id` с текстом `Email: alice@example.test` → email маскируется, текст вне email (`Email: `) не меняется;
3. повтор исходного текста → та же маска;
4. отправка маски → точный исходный текст;
5. повтор маски → тот же исходный текст.

Каждый шаг печатает `PASS`; при любой ошибке скрипт печатает `FAIL: <причина>` в stderr и завершается с кодом 1. Адрес по умолчанию — `http://127.0.0.1:8000`; передаётся только базовый HTTP(S)-адрес без пути, учётных данных и query. Скрипт использует только стандартную библиотеку Python 3 и не требует внешних зависимостей.

### Дистрибутив

Файлы `compose.server.yml`, `init-deploy-env.py` и `smoke-deploy.py` включены в исходный дистрибутив `scripts/make-dist.sh` (см. список `FILES`), поэтому развёртывание и проверка доступны из архива без дополнительной сборки.

## HTTP API

`POST /process`, `Content-Type: application/json`. Авторизация на этом endpoint не требуется.

Запрос:

```json
{"payload":"текст","payload_id":"уникальный идентификатор"}
```

Оба поля обязательны. `payload_id` должен быть непустым. Пустой `payload` допустим и возвращается без изменения. Тело должно быть единственным JSON-объектом; неизвестные поля отклоняются. Размер тела ограничен (`PII_MAX_BODY_BYTES`).

Успешный ответ — HTTP 200:

```json
{"result":"обработанный текст"}
```

Поведение:

- Новый `payload_id` и исходный текст → маскированный текст.
- Тот же ID и полученная маска → точный исходный текст, включая пробелы и пунктуацию.
- Тот же ID и исходный текст → та же маска (повтор).
- Тот же ID и текст, не совпадающий ни с оригиналом, ни с маской → HTTP 409.
- Если персональных данных нет и исходный текст совпадает с результатом, повторы возвращают этот же текст.
- Направление операции определяется по состоянию и входным данным, а не числом обращений.
- Одновременные запросы с одним ID дают согласованный результат; создание соответствия атомарно.
- Соответствие не удаляется сразу после первого восстановления: ответ может потеряться и вызвать повтор.

Ошибки возвращаются в согласованном JSON `{"error":"..."}` без исходного текста, найденных значений и ключей. Коды: `400` — неверный запрос, `409` — конфликт текста с известным ID, `413` — превышение размера тела, `429` — перегрузка или нехватка ресурсов хранилища (с заголовком `Retry-After`), `500` — внутренняя ошибка.

Дополнительные поля в запросе не поддерживаются и отклоняются как неверный запрос.

## Управляемые системы-потребители

Для систем-потребителей добавлены явные endpoint-ы `POST /v1/mask` и `POST /v1/restore`. Оба принимают `{"payload":"...","payload_id":"..."}` и возвращают `{"result":"..."}`. Система аутентифицируется по заголовку `Authorization: Bearer <API key>`; её идентичность определяется на сервере по секрету и не может быть подменена полем или заголовком запроса.

- `POST /v1/mask` — операция всегда маскирует. Передача ранее выпущенной маски не переключает её на демаскирование: возвращается та же маска.
- `POST /v1/restore` — подставляет таблицу замен нужной системы и ID внутри переданного текста. Текст может быть новым, с переставленными или повторёнными собственными маркерами. Сохранённый оригинал целиком вместо подстановки не возвращается.

Формат маски закрепляется за созданной записью. Основной формат — различимые маркеры `[PII_N]`, поддерживающие подстановку в изменённом тексте. Второй формат — звёздочки `****`; он неоднозначен в изменённом тексте, поэтому ограничен точным восстановлением собственной маски и не обещает произвольную подстановку. Текущие права доступа (включение, право восстановления) проверяются при каждой операции.

Ошибки аутентификации и прав: `401` — недействительный или отсутствующий API key, `403` — система отключена, маскирование выключено или восстановление запрещено, `404` — соответствие для ID не найдено. Ошибки `409`, `413`, `429`, `500` — как у `/process`.

### Конфигурация потребителей

Системы-потребители и regexp-правила задаются JSON-файлом, путь к которому указывается в `PII_CONSUMERS_FILE` (пример — `config/consumers.example.json`). Для каждой системы настраиваются `enabled`, перечень защищаемых типов, включение маскирования, право восстановления и формат маски. Секреты подключаются через окружение (`secret_env`) или файл (`secret_file`); в репозитории хранятся только имена переменных, без значений.

Вся конфигурация валидируется целиком до запуска: невалидный regexp, неизвестный тип, пустой секрет или неверный формат отклоняют старт без частичного применения.

### Новые типы данных

Новый тип добавляется через реестр распознавателей и конфигурацию. Для типа без нового Go-кода используется ограниченное правило на стандартном `regexp` с типом и приоритетом: компиляция при запуске, проверка параметров, лимиты числа правил и совпадений. Исполняемый язык выражений и загрузка плагинов не вводятся.

## Здоровье

- `GET /livez` — процесс жив.
- `GET /readyz` — конфигурация и обязательные зависимости инициализированы.

Оба endpoint-а возвращают фиксированный статус и никогда не возвращают пользовательские данные.

## Наблюдаемость

### Метрики

`GET /metrics` отдаёт метрики в формате Prometheus text, который можно опросить локально. Метки берутся из ограниченного фиксированного набора (операция, исход, класс длительности, причина отказа хранилища); `payload_id`, текст, найденные значения и имена потребителей из тела запроса в метки не попадают.

- `pii_requests_total{operation,outcome}` — число запросов и результаты отдельно по операции (`process`/`mask`/`restore`) и исходу (`mask`, `restore`, `repeat`, `conflict`, `error`, `overload`, `cancel`, `invalid`, `too_large`, `unauthorized`, `forbidden`, `not_found`, `method_not_allowed`).
- `pii_response_duration_seconds{operation,class}` — гистограмма длительности ответа сервиса, позволяющая вычислить среднее и p50/p95/p99. Интервал измеряется от приёма запроса до завершения записи ответа (включая сериализацию и запись, насколько их может наблюдать сервер). Чтение тела ответа клиентом — отдельное измерение и в эту метрику не входит. Класс `success` отделён от быстрых `overload` и `error`, чтобы перцентили не искажались дешёвыми 429. Гистограмма не хранит каждую длительность в обработчике.
- `pii_active_requests` — активные запросы.
- `pii_text_bytes_total{operation}`, `pii_text_chars_total{operation}` — объём текста в байтах и символах (кодовых точках).
- `pii_tokens_total{operation,method}` — оценка токенов с явно названным методом подсчёта (`estimate_runes_div4`). Точный токенизатор не задан, поэтому длина в байтах никогда не выдаётся за число токенов.
- `pii_store_records`, `pii_store_bytes` — текущие записи и учтённые байты хранилища.
- `pii_store_ttl_expired_total` — истечения TTL.
- `pii_store_failures_total{reason}` — отказы хранилища (`capacity`, `busy`).

Экспорт метрик не создаёт неограниченной очереди и не задерживает запрос при недоступном приёмнике: сборка ответа выполняется на месте по запросу.

### Структурированные логи

Логи пишутся через `slog` и содержат этапы обработки: `accept` (принятие), `operation` (определение операции с направлением), `recognition` (распознавание с типами сущностей), `replacement` (замена), `storage` (хранение), `restoration` (восстановление) и `complete` (завершение с исходом). Каждый запрос получает технический идентификатор `request_id`, создаваемый на сервере отдельно от пользовательского `payload_id`.

В логи попадают типы сущностей и классы ошибок, но не текст, найденные значения, секреты и таблицы замен. `payload_id` в логи не выводится.

Отладочные профили (`pprof`) на общедоступном listener не открываются.

### Правила распознавания

Каждый распознаватель возвращает фрагменты общего типа `Fragment` (тип данных + байтовый диапазон в исходном тексте). Нормализация (удаление разделителей) применяется только для распознавания; диапазоны всегда указываются в исходном тексте, поэтому восстановление точное. Скомпилированные правила создаются при инициализации пакета.

- **Email** — общее правило: локальная часть, `@`, домен с точкой.
- **Телефон** — 11 цифр, начинается с 7 или 8. Формы `+7`, `8` и контекстные слова (`телефон`, `тел`, `мобильный`) считаются явным признаком; голый номер без префикса и контекста не маскируется.
- **ИНН** — 10 или 12 цифр. Контрольная сумма — сигнал; явно подписанный ИНН (`ИНН`, `inn`) маскируется даже при неверной контрольной цифре.
- **Номер карты** — 13–19 цифр. Проверка Луна — сигнал; явно подписанная карта (`карта`, `card`) маскируется даже при неверной контрольной цифре.
- **Серия и номер паспорта** — 4+6 цифр. Требуется контекст (`паспорт`, `серия`), чтобы не маскировать номера заказов.
- **Код подразделения** — `XXX-XXX` с обязательным дефисом и контекстом (`код подразделения`).
- **Серия и номер водительского удостоверения** — 4+6 цифр. Требуется контекст (`водительское удостоверение`, `права`).
- **ПИН** — 4 цифры. Случайные четыре цифры не считаются секретом; требуется контекст (`пин`, `пин-код`, `pin`).
- **CVV** — 3 цифры. Случайные три цифры не считаются секретом; требуется контекст (`cvv`, `код безопасности`).
- **ФИО** — 2–3 слова с заглавной буквы или форма с инициалами (`Иванов И. И.`, `И. И. Иванов`). Требуется роль клиента рядом (`фио`, `фамилия`, `имя`, `отчество`, `клиент`, `заявитель`, `владелец`, `держатель`, `гражданин`, `родился`, `проживает`, `зарегистрирован`, `паспорт`, `выдан`). Явно подписанные поля (`фио`, `фамилия`, `отчество`) поддерживают верхний, нижний и смешанный регистр значения; `имя` вводит одиночное имя с заглавной буквы. Справочное упоминание человека (например, «поэт Александр Пушкин») не маскируется, в том числе когда клиентская подпись есть в том же предложении, но имя вводится справочным маркером роли (`поэт`, `писатель`, `художник` и т.п.) — это маркеры роли, а не список исключённых имён. Клиент, действительно носящий имя, маскируется, когда подпись вводит его напрямую («Клиент Александр Пушкин»), при этом сама подпись в маску не входит. Одиночная фамилия/имя/отчество распознаётся после подписи `фамилия`/`имя`/`отчество`. Поддержаны только перечисленные формы; общая морфология не заявляется.
- **Дата рождения** — дата числами (`12.03.1990`) или словами (`12 марта 1990 года`, месяц в любом регистре) после подписи `дата рождения` (или `родился`/`родилась`). Голая дата не сообщает свою роль и не маскируется.
- **Место рождения** — обозначение места (`г. Москва`, `в Москве`) после подписи `место рождения` (или `родился`/`родилась`). После явной подписи `место рождения` принимается и голое название города (`Казань`). Требуется маркер места или предлог `в` после «родился», чтобы имя человека не принималось за место.
- **Гражданство** — название страны из фиксированного словаря (включая распространённые падежные формы) рядом с подписью `гражданство`/`гражданин`/`гражданка`. Словарь исключает путаницу имени человека с гражданством.
- **Орган выдачи паспорта** — последовательность слов с заглавной буквы и сокращений после подписи `выдан`/`кем выдан`/`орган выдачи` (например, `ОУФМС России по г. Москве`).
- **Дата выдачи паспорта** — дата после подписи `дата выдачи` (или `выдан`/`выдано`). Отдельная категория от даты рождения: подпись решает, к какой категории относится дата.
- **Адрес и его части** — последовательность составных частей (`г. Москва, ул. Ленина, д. 5, кв. 10`) с ближайшим владельцем. Составные названия сохраняют связь: дефисные города (`Санкт-Петербург`), многословные улицы (`Большая Морская`), буквенные номера домов (`д. 12А`) и длинные последовательности частей остаются одним фрагментом. Адрес клиента (`адрес клиента`, `проживает`, `зарегистрирован`) маскируется; адрес банковского отделения (`адрес отделения`, `банк`, `офис`) — нет. Исключение относится к роли конкретного фрагмента, а не к глобальному запрету слова «банк».
- **Имя держателя карты** — 1–3 слова с заглавной буквы (латиницей или кириллицей) после подписи `держатель карты`/`card holder`/`имя на карте`/`name on card`.

Номера заказов, суммы и обычные даты не маскируются только из-за подходящей длины: слова `заказ`, `order`, `сумма`, `amount`, `дата`, `date` рядом с числом подавляют распознавание. Положительный и отрицательный контекст привязан к конкретному значению и границам поля: поле ограничено `;` или переводом строки, поэтому слово `дата` или `сумма` в соседнем поле не подавляет чувствительный реквизит в своём поле (например, «Дата выдачи: 01.01.2020; паспорт 4510 123456» маскирует и дату, и паспорт).

Пересечения фрагментов разрешаются детерминированно общим механизмом: одинаковые и вложенные диапазоны не порождают двойную замену, а частичное пересечение покрывается объединением диапазонов (тип берётся у более приоритетного), не расширяясь до всей строки, — ни один чувствительный байт не остаётся открытым. Внутренне некорректный диапазон (вне границ, инвертированный или не на границе руны) приводит к ошибке защиты, и операция завершается с ошибкой, не отправляя частично замаскированный текст.

Формат замены — маркеры вида `[PII_N]`, не конфликтующие с уже имеющимся текстом. Скрываются только найденные фрагменты. Цель качества — 95%; точный способ расчёта не задан.

Считать успешные операции, повторы, 429 и ошибки отдельно. Измерять CPU, память и размеры входов. Ограничивать число активных запросов до чтения больших тел. Проверить точное восстановление, повторы после потери ответа, конкурентные обращения и истечение срока хранения.

Измеренный практический предел сервиса — около 1500 RPS суммарно (при 200 соединениях и 2 CPU / 512 MiB): на 2000 RPS появляются таймауты клиента и рост p99. Целевые 330 RPS в среднем с пиками до 1000 достигаются с запасом (p99 ≈ 0.5 с).

## Настройки и защита

Для каждой системы-потребителя настраиваются доступ, набор типов данных, включение маскирования и право восстановления. Состояние разных систем изолировано. Внутренний ключ записи — «область потребителя + `payload_id`». Для `/process` используется одна фиксированная область, не выбираемая из заголовков или полей запроса. Имя потребителя не должно совпадать с зарезервированной областью `process` и не должно содержать разделитель `:`, иначе его ключ совпал бы с публичной областью или областью другого потребителя; такая конфигурация отклоняется при старте. Новые типы данных должны добавляться без переписывания ядра.

В логах — этапы обработки и типы найденных данных. Исходные тексты, значения и ключи туда не попадают. Метрики: время ответа, запросы и токены в секунду; приблизительный подсчёт токенов обозначается явно. Значения данных и `payload_id` не используются в метках метрик.

### Хранилище и координация

Хранилище — in-memory, с лимитами на число записей, размер одной записи и общий объём. Учёт байтов приблизительный: включает ключ записи (область + `payload_id`), исходный текст, маску, таблицу замен и фиксированные накладные расходы на запись и элемент таблицы; корректность проверяется по RSS. Ключ учитывается, потому что `payload_id` может занимать почти всё тело запроса и затем хранится как ключ карты. При исчерпании ёмкости новый запрос получает `429` и не удаляет действующие соответствия — предпочтителен контролируемый отказ. Публичная область `/process` использует отдельный экземпляр хранилища, поэтому исчерпание её ёмкости не влияет на управляемых потребителей и наоборот. Перед выполнением распознавания хранилище отклоняет запрос, если оно уже на пределе ёмкости, чтобы не тратить ресурсы на заведомо несохраняемый запрос.

Предел размера одной записи (`PII_STORE_MAX_RECORD_BYTES`, по умолчанию 4 MiB) ограничивает цикл маскирование → восстановление для больших текстов. Текст на 100 000 токенов (~748 КБ) вместе с маской и таблицей замен сохраняется и восстанавливается точно. Таблица замен хранит маркеры и байтовые диапазоны в исходном тексте, а не копии значений, поэтому запись не дублирует сущности: размер записи ≈ исходный текст + маска + маркеры. Текст с очень плотным списком сущностей (например, десятки тысяч email в одном теле) может превысить лимит записи и отклоняется `429` — это предсказуемый отказ, а не обрезка списка сущностей.

Создание соответствия для одного ключа атомарно и координируется через явное резервирование: первый запрос ключа выполняет распознавание и публикует запись, остальные ждут его результат (с учётом `context` и предела `PII_STORE_CREATE_WAIT`). Общий mutex не удерживается во время распознавания, поэтому разные ключи обрабатываются независимо. Отмена создателя освобождает резервирование без частичного состояния; ожидающий запрос при отмене создателя повторяет попытку.

Запись становится видимой целиком до ответа `200`. Если клиент потерял ответ, повтор исходного текста возвращает сохранённую маску. Для готовой записи повтор использует сохранённую маску даже после изменения правил распознавания.

Срок хранения (`PII_STORE_TTL`) выбирается с запасом на пару запросов и повторы; по умолчанию `24h`. Просроченные записи удаляются фоновой задачей (`PII_STORE_CLEANUP_INTERVAL`) и лениво при обращении к конкретному ключу. Проверка TTL конкретного ключа ограничена по стоимости: она не обходит всю карту, а смотрит только на запрошенный ключ. Остальные просроченные записи освобождаются через кучу сроков истечения: фоновая задача и операция при заполнении выгружают из кучи только реально просроченные записи, поэтому стоимость очистки не растёт с числом живых соответствий. Фоновая задача принадлежит хранилищу и останавливается с проверяемым завершением при остановке сервиса.

Бюджет памяти при лимите контейнера 512 MiB: два экземпляра хранилища (публичная область `/process` и управляемые потребители) по умолчанию ограничены `PII_STORE_MAX_BYTES = 64 MiB` каждый, то есть до 128 MiB суммарно. Рабочие данные HTTP и распознавания ограничены суммарным бюджетом `PII_MAX_WORKING_BYTES = 64 MiB`: каждый запрос резервирует долю бюджета до чтения тела, пропорциональную заявленному `Content-Length` (оценка пиковой временной памяти: буфер тела + полезная нагрузка + маска + таблица замен), и при исчерпании бюджета получает `429`. Это ограничивает суммарную временную память многих одновременных больших запросов, включая буферы тел, чего не гарантирует только лимит тела запроса. Тела запросов ограничены `PII_MAX_BODY_BYTES = 2 MiB` каждое, активные запросы — `PII_MAX_ACTIVE_REQUESTS = 200`. Образ запускается с `GOGC=50`, чтобы рантайм Go собирал мусор агрессивнее и куча не росла между всплесками больших запросов. Учёт байтов хранилища и оценка рабочего бюджета приблизительные и проверяются по RSS; при необходимости бюджет пересматривается через настройки, а не через превышение лимита контейнера.

|---|---|---|---|---|---|

### Ограничение восстановления без состояния

Если срок хранения истёк, соответствие утрачено, и клиент повторно присылает ранее выданную маску, сервис не может восстановить оригинал: без сохранённого соответствия маска неотличима от обычного текста. Такая маска обрабатывается как новый исходный текст и возвращается без изменений (формат `[PII_N]` не распознаётся как персональные данные текущими распознавателями). Восстановление без состояния не обещается. Если будущий распознаватель начнёт распознавать формат маски, утраченное соответствие не должно незаметно возвращаться как успешный новый результат — для этого потребуется явная политика для текста, совпадающего с форматом маркера.

## Демонстрация

Синтетический текст → маскирование → демонстрационный ответ LLM → восстановление значений для потребителя с соответствующим правом. Реальный вызов модели необязателен. Ошибка маскирования не должна разрешать отправку открытого текста в модель.

### Локальная команда демонстрации

```sh
go run ./cmd/demo
```

Команда собирает сервис в процессе, поднимает реальные endpoint-ы `/v1/mask` и `/v1/restore` и выполняет сценарий от начала до конца без внешнего провайдера и ключа. Используется отдельный настроенный потребитель `demo` с различимым форматом маркеров `[PII_N]`. Демонстрационная модель — детерминированная реализация за небольшим интерфейсом `demo.Model`; она переставляет собственные маркеры, повторяет один и опускает другой, поэтому восстановление проверяется внутри изменённого ответа. Ответ модели подписан как демонстрационный (`[demo]`).

На экран выводятся синтетический оригинал, маска, ответ модели и восстановленный ответ. Секрет аутентификации не печатается, а производственные логи сервиса не получают эти тексты. Команда также показывает защиту при ошибке маскирования (модель не вызывается), отказ в праве восстановления и отдельный явно настроенный сценарий с выключенным маскированием, который не представлен как защищённый.

Проверки сценария находятся в `internal/demo/demo_test.go`: модель получает именно маску, восстановление работает внутри изменённого ответа, чужие маркеры, другой ID, другой потребитель и отсутствие права не раскрывают значения, а также проверены ошибка маскирования, ошибка модели и отсутствие соответствия.

## Структура

- `cmd/pii-service/` — точка входа, явная сборка зависимостей.
- `cmd/demo/` — локальная команда демонстрации цикла маскирование → модель → восстановление (in-process сервис).
- `cmd/demo-remote/` — демонстрация цикла против запущенного сервиса через реальные `/v1/mask` и `/v1/restore`.
- `cmd/loadtest/` — воспроизводимый нагрузочный генератор для `/process` (см. «Нагрузочный инструмент»).
- `cmd/eval/` — локальная оценка распознавания по синтетическому набору всех 17 категорий.
- `internal/demo/` — интерфейс демонстрационной модели, HTTP-клиент `/v1/mask` и `/v1/restore`, оркестрация сценария и его проверки.
- `internal/loadgen/` — генератор синтетических текстов, HTTP-клиент с повторами, распределения операций, планировщик и сбор статистики для нагрузочного инструмента.
- `internal/config/` — проверяемые настройки с объяснёнными значениями по умолчанию; конфигурация потребителей и regexp-правил.
- `internal/recognizer/` — распознаватели фрагментов (тип + диапазон в байтах UTF-8), общий механизм разрешения пересечений, реестр типов и regexp-правила.
- `internal/masker/` — замена фрагментов маркерами и звёздочками, восстановление.
- `internal/store/` — хранилище соответствий (лимиты, TTL, атомарное создание, резервирование ключа, фоновая очистка).
- `internal/app/` — прикладной слой: политика потребителя, направление операции, конфликт, маскирование и восстановление.
- `internal/httpapi/` — HTTP-обработчики, аутентификация по API key, граница транспорта, технический идентификатор запроса и запись метрик.
- `internal/metrics/` — коллекторы Prometheus на приватном реестре, оценка токенов и HTTP-обработчик `/metrics`.
- `internal/eval/` — набор данных, генератор вариантов и метрики оценки распознавания.
- `config/` — примеры настроек без секретов.
- `tests/` — контрактные и интеграционные проверки.
- `Dockerfile` — многоэтапная сборка (Go 1.27.1 из `go.mod`, финальный образ distroless non-root).
- `docker-compose.yml` — локальная конфигурация запуска: порты, лимиты ресурсов, read-only ФС, tmpfs, секреты через окружение.
- `Makefile` — команды сборки, запуска, остановки, тестов и демонстрации.

### Нагрузочный инструмент

`cmd/loadtest` — воспроизводимый нагрузочный генератор для `POST /process`. Он заранее генерирует синтетические тексты из разных категорий с фиксированным seed (`20260922`), поэтому стоимость генерации входов не приписывается сервису. Пары связываются уникальным `payload_id`: прямой шаг отправляет исходный текст и получает маску, обратный отправляет маску и проверяет точное восстановление. Повтор при ошибке или 429 использует тот же ID и текст, не более трёх попыток, с учётом `Retry-After`. Таймаут клиента — 10 с.

```sh
# Основной профиль: разгон, ~330 RPS в среднем, пики до 1000, 200 соединений, ~5 минут
go run ./cmd/loadtest -base http://127.0.0.1:8080 -mode sequential \
  -duration 5m -target 330 -peak 1000 -ramp 60s \
  -burst-every 60s -burst-duration 5s -workers 200 -out .artifacts -container pii-service

# Распределения операций
go run ./cmd/loadtest -mode mask_dominant -restore-fraction 0.3 ...   # преобладание новых масок
go run ./cmd/loadtest -mode restore_dominant -prep 20000 -restore-budget 2 ...  # восстановление из подготовленного набора

# Отдельные режимы
go run ./cmd/loadtest -large-text ...   # большие тексты до 100 000 токенов и плотный список сущностей
go run ./cmd/loadtest -scheduled ...    # отправка по расписанию с ограниченной очередью
go run ./cmd/loadtest -compat ...       # остановка после пяти невалидных ответов подряд
```

Три распределения: последовательные пары; преобладание новых маскирований с ростом числа ожидающих пар; преобладание восстановлений из заранее созданного набора (стоимость и размер подготовки показываются отдельно, успешное восстановление не повторяется бесконечно под одним ID). Отчёт содержит целевой/фактический/успешный RPS, пропуски генератора, среднее/p50/p95/p99 по операциям и исходам, 429, ошибки, таймауты, CPU/RSS и динамику хранилища. Результаты сохраняются в `.artifacts/` и не содержат секретов.

Режим `-large-text` проверяет полный цикл маскирование → восстановление для текстов на 10k/50k/100k токенов (оценка `runes/4`) и для текста с плотным списком сущностей (много email в одном теле). Отчёт зависит от ответа текущего сервиса: текст внутри заявленного профиля должен вернуть `200` при маскировании и точное восстановление, а превышение заявленного предела — предсказуемый отказ. Для каждого размера выводятся байты, руны, способ оценки токенов, latency маскирования и восстановления и точность восстановления; в конце — peak RSS.

Проверка совместимости останавливает прогон после пяти невалидных ответов подряд: 429 не увеличивает и не сбрасывает счётчик, успех сбрасывает. Генератор сообщает фактическую причину ранней остановки.

### Локальная оценка распознавания

Одна команда строит таблицу метрик и список ошибок по синтетическому набору, покрывающему все 17 категорий:

```sh
go run ./cmd/eval            # печать в stdout
go run ./cmd/eval -out tests/eval-results.txt   # сохранить отчёт в файл
```

Набор содержит только синтетические данные. Каждый пример — исходный текст и ожидаемые непересекающиеся диапазоны с категориями в байтовых смещениях UTF-8 (та же единица, что использует сервис). Разметка валидируется отдельно: диапазоны внутри строки, на границах рун и без пересечений. Примеры разделены на набор для разработки и отложенный набор; генератор вариантов использует фиксированный seed (`20260922`), поэтому повтор с тем же seed воспроизводит результат. Пример из отложенного набора, использованный для исправления, переносится в регрессионные тесты и заменяется новыми независимыми вариантами.

Метрики считаются локально и явно, единица подсчёта символов — байты UTF-8:

- полнота и точность по диапазонам с точным совпадением границ (per-category);
- покрытие чувствительных байтов и лишнее скрытие обычных байтов, без повторного счёта пересечений (по объединению диапазонов);
- ошибки определения категории отдельно от фактического сокрытия;
- точность восстановления исходного текста и неизменность текста вне масок.

Результаты показываются по каждой категории отдельно, с численностью примеров и отрицательными случаями, чтобы большой набор телефонов не скрывал провал по адресам. Ограниченные fuzz-проверки (`FuzzRestoreUnicode`, `FuzzOverlapResolution`, `FuzzMaskerRestore`) проверяют Unicode, пересечения и точное восстановление.

```sh
go test ./internal/eval/ -run=^$ -fuzz=FuzzRestoreUnicode -fuzztime=15s
go test ./internal/eval/ -run=^$ -fuzz=FuzzOverlapResolution -fuzztime=15s
go test ./internal/eval/ -run=^$ -fuzz=FuzzMaskerRestore -fuzztime=15s
```

Актуальный отчёт сохранён в `tests/eval-results.txt`.

## Схема компонентов

Один Go-процесс с явной сборкой зависимостей в точке входа. HTTP-слой разбирает запрос и выбирает ответ на границе транспорта; прикладной слой координирует политику потребителя, распознавание, замену и хранение; распознаватели и хранилище изолированы за интерфейсами.

```
                    ┌────────────────────────────── pii-service ──────────────────────────────┐
  POST /process ───▶│  httpapi (лимит активных, auth, request_id, метрики)                    │
  POST /v1/mask ───▶│      │                                                                  │
  POST /v1/restore─▶│      ▼                                                                  │
  GET /livez,/readyz│  app (направление, конфликт, политика потребителя)                      │
  GET /metrics ────▶│      │                        │                                         │
                    │      ▼                        ▼                                         │
                    │  recognizer (17 типов,      store (in-memory: лимиты, TTL,              │
                    │  пересечения, regexp-правила)  атомарное создание, резервирование)      │
                    │      │                        │                                         │
                    │      ▼                        │                                         │
                    │  masker (маркеры [PII_N] / звёздочки, восстановление)                   │
                    └─────────────────────────────────────────────────────────────────────────┘
```

Поток одного запроса: `httpapi` → `app` → `recognizer` (фрагменты в байтовых смещениях UTF-8) → `masker` (замена) → `store` (атомарное сохранение соответствия) → ответ. Восстановление читает таблицу замен из `store` и подставляет маркеры в текст. `/process` использует отдельный экземпляр хранилища, поэтому не исчерпывает ёмкость управляемых потребителей.

## Демонстрация за минуту

`go run ./cmd/demo` поднимает сервис в процессе и выполняет цикл: синтетический текст → маска → детерминированный ответ «модели» → восстановление. Модель получает только маску (исходные значения не уходят), переставляет и повторяет маркеры, поэтому восстановление проверяется внутри изменённого ответа. Команда также показывает защиту при ошибке маскирования (модель не вызывается), отказ в праве восстановления и сценарий с выключенным маскированием. Против запущенного контейнера тот же цикл выполняет `make demo` (потребитель `demo`).
